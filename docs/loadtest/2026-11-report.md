## 7. Temuan dan perbaikan

### 7.1 Snapshot memuat semua profil publik → biaya O(jumlah akun) per request (diperbaiki, default menunggu keputusan)

`buildSnapshot` memanggil `ListUsers` + `publicStats` untuk **semua** user di setiap snapshot non-admin. Dengan 3.000
akun, tiap `GET /api/v1/state` membangun ±3.000 profil, ±66 ribu alokasi, dan ±900 KB JSON, padahal tamu atau user
biasanya hanya butuh puluhan profil (pemilik listing aktif dan pihak booking/ulasan). Di VPS 1+1 CPU, ini menghabiskan
CPU API dan menahan koneksi pool, sehingga **semua** endpoint ikut lambat.

Perbaikan (`internal/service/snapshot.go`, `ListUsersByIDs`, env `SNAPSHOT_USERS`):

- `referenced`: user dimuat **terakhir**, hanya yang dirujuk isi snapshot. Yang dirujuk: viewer, `u-admin`, pemilik
  listing, penulis + target ulasan, peminta papan + penawar, pihak booking, pengirim pesan, pembuka sengketa,
  pelapor + target laporan user, strike, dan verifikasi. `publicStats` juga hanya dihitung untuk id itu
  (`WHERE $2::text[] IS NULL OR u.id = ANY($2)`). Admin dan scope `full` tetap memuat semua.
- Default `all` (perilaku lama). Validasi di `internal/config` (nilai lain = gagal start).
- Tes: `TestSnapshotUsersReferenced` (yang dirujuk lengkap dengan data publik + reputasi yang sama dengan `all`, user
  tanpa rujukan tidak terlihat, profil sendiri lengkap, admin semua), `TestSnapshotUsers` (config),
  `BenchmarkSnapshot` (regresi biaya).
- Dampak ke web: `/u/[id]` untuk user yang tidak dirujuk (mis. penyewa tanpa ulasan yang dibuka lewat tautan
  langsung) tidak menemukan profil di snapshot. Tautan di dalam aplikasi selalu berasal dari data yang dirujuk.
  Pilihan: endpoint `GET /api/v1/users/{id}` (profil publik) untuk halaman itu. **Sudah ditanyakan ke koordinator.**
- Bonus privasi (UU PDP, minimisasi data): tamu tidak lagi menerima nama depan semua anggota.

### 7.2 ETag global: rasio 304 = 0% di semua run (rekomendasi, belum diubah)

`ETag` = hash(`max(change_log.version)`, scope, viewer, jam, jendela 15 menit). Setiap commit di mana pun menaikkan
versi, jadi di bawah lalu lintas tulis apa pun (bahkan hanya `toggleFavorite` 2,7/detik di campus-nat), **tidak ada satu
pun** refetch yang mendapat 304. Di 5 run yang diperiksa (staging main + NAT, lt-base-3k, lt-base-nat,
lt-ref-vps-3k: 24.094 request `state`), semuanya 200.

`change_log` sudah mencatat `users`, `admins`, dan `public` (dipakai realtime). ETag per viewer bisa memakai versi
terakhir yang relevan untuk viewer itu (`public OR $me = ANY(users) OR (admins AND admin)`). Tapi ini baru aman
setelah 7.3 diperbaiki, dan field `version`/`bookingCounter` di body ikut berubah maknanya. Wilayah core-v2 + web.

### 7.3 Perubahan `listingBusy`/reputasi tidak ditandai publik (bug realtime, dilaporkan)

`txn.saveBooking` hanya memanggil `touch(renter, provider)`, tidak `touchPublic()`. Padahal booking yang menjadi
`ACCEPTED`/`ACTIVE`/`DISPUTED`/`COMPLETED` mengubah data publik di snapshot: `listingBusy` (tanggal terpakai) dan
`publicStats` (sewa selesai, sengketa). Akibatnya tamu dan user lain **tidak menerima event `changed`** saat kalender
listing berubah, sehingga kalender di halaman barang bisa basi sampai ada event publik lain. Usul: `touchPublic()` di
`saveBooking` saat status masuk/keluar himpunan sibuk atau menjadi `COMPLETED`. Tidak saya ubah (wilayah core-v2).

### 7.4 Ukuran pool pgx

Default 8 (= CPU container). Pada beban normal (≤ 600 VU di host ini) hampir tidak pernah antre (≤ 0,6%). Pool baru
jenuh saat CPU sudah jenuh. Menaikkan ke 16 pada 900 VU hanya memperbaiki p95 ±20–35%, karena leher botolnya CPU,
bukan koneksi. Ukuran bisa diatur tanpa kode lewat parameter pgx bawaan `DATABASE_URL=...&pool_max_conns=N`
(terverifikasi: `sewain_db_pool_max_conns 16`). Saran: 16 di server ini, 8 di VPS 2 vCPU. Selalu jauh di bawah
`max_connections` (100).

### 7.5 Lain-lain

- **Query:** tidak ada query lambat. `publicStats` 2,9 ms, pencarian PostGIS p95 ≤ 3 ms di staging. Tidak ada lock
  wait. Tidak perlu indeks baru.
- **Kompresi:** Caddy sudah mengirim `zstd`/`gzip` (`/state` 1 MB → ±40 KB, 217 KB → ±10 KB). Bandwidth tunnel aman
  (±7 Mbit/s pada 300 VU dengan 3.000 akun tanpa perbaikan).
- **Rate limit:** 0 respons 429 di semua run, termasuk 300 VU dari satu IP. `prepare` (±1.000 request dari banyak
  IP dalam 3–8 detik) juga tidak kena 429.
- **Unggahan:** p95 17–28 ms untuk 125 KB. Inspeksi/dekode gambar tidak jadi masalah pada 5% VU.
- **Staging dipakai bersama:** reset/deploy di tengah uji membuat hasil tidak sah tanpa tanda yang jelas (403 cepat
  terlihat seperti "lolos"). Runner sekarang berhenti sendiri setelah 5 respons 401/403 pada sesi pool.

4. `pool_max_conns=16` di server ini, 8 di VPS.
5. Ulangi uji ini setelah 7.2/7.3 dikerjakan dan sebelum promosi besar (PRD §18).
